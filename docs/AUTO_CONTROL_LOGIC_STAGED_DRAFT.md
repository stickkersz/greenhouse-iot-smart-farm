- fan-lock-decouple — ship **v2.6.0 (2026-07-23)** · ถอด `fanLockUntil` + gate ใน `autoControl()`, `pumpSafetyCheck()` ตัดเฉพาะปั๊ม, `status/fan_locked` คงไว้ false

## สรุปผลสุดท้าย (อ่านแค่นี้พอถ้าจะ implement)

**ไม่ทำ fan-speed staging, ไม่ทำ fan-start-delay, ไม่สลับลำดับปั๊ม/พัดลมตาม hot+dry vs hot+humid** (พิจารณาทั้งหมดแล้วตัดออก — เหตุผลอยู่ท้ายไฟล์) **auto_control_logic.h เดิมถูกต้องอยู่แล้ว** การเปลี่ยนแปลงจริงมี 2 จุด ทั้งคู่อยู่ใน `.ino` ล้วนๆ ระดับ safety-timer/relay-wiring ไม่ใช่ระดับ decision-logic:

| ค่า/พฤติกรรม | เดิม | ใหม่ |
|---|---|---|
| `PUMP_MAX_RUNTIME_MS` | 10 นาที | **15 นาที** |
| `PUMP_COOLDOWN_MS` | 5 นาที | **5 นาที (ไม่เปลี่ยน)** |
| พัดลมตอนปั๊ม cutoff | **ดับพร้อมปั๊มเสมอ (hard lock 5 นาที ไม่มี hot override)** | **แยกออกจากกัน — พัดลมทำงานตาม `dec.fanOn` อิสระ ไม่ถูกล็อกตามปั๊ม** |

## ทำไมถึงต้องแก้ — หลักฐานจากข้อมูลจริง (2026-07-20)

1. **CSV `smartfarm_24h_2026-07-20.csv`**: อุณหภูมิ ≥34°C ต่อเนื่อง **7 ชั่วโมง** (11:00-17:00) เฉลี่ย **37.1°C** สูงสุด 38.8°C ทั้งที่ความชื้นช่วงนั้นแค่ 43-49% (แห้ง เข้าเงื่อนไข evaporative cooling ที่ควรได้ผลดีที่สุด)
2. Nattakit Prasertsak ยืนยันว่า **ปั๊ม+พัดลมตัดทุก 10 นาทีตลอดช่วงนั้น** (ตามดีไซน์ safety cutoff เดิม)
3. คำนวณ duty cycle: 10 นาทีเดิน + 5 นาทีพัก (hard lock ทั้งคู่) = **33% ของเวลาไม่มีอะไรทำงานเลย** แม้อุณหภูมิจะวิกฤตแค่ไหนก็ตาม — ยืด runtime เป็น 15 นาทีอย่างเดียวลดเหลือแค่ 25% ยังไม่พอน่าจะอธิบาย overshoot ขนาดนี้ได้
4. เทียบกับสภาพอากาศจริงวันเดียวกัน (weather widget, Nonthaburi, จันทร์ 16:00): ข้างนอก 35°C ชื้น 47% — เกิน 34°C ที่เป็นเป้าหมายไปแล้วตั้งแต่ยังไม่นับความร้อนที่โรงเรือนดักเพิ่ม (greenhouse effect ~5-6°C ในเคสนี้ ถือว่าไม่ผิดปกติ) แปลว่าวันร้อนแบบนี้ต้องพึ่ง evaporative cooling ทำงาน**ต่อเนื่อง**จริงๆ ถึงจะมีโอกาสต่ำกว่า 34°C ได้ — การที่ระบบดับไปมา 1 ใน 3 ของเวลาคือตัวขวางหลัก
5. **สรุป: root cause คือ pump-safety hard-lock ที่ดึงพัดลมดับไปด้วยทุกครั้ง ไม่ใช่เรื่องลำดับเปิดปั๊ม/พัดลม** (ดูหัวข้อ "แนวคิดที่พิจารณาแล้วไม่ทำ" ด้านล่างว่าทำไมข้อเสนอเรื่องสลับลำดับถึงไม่ช่วยแก้ปัญหานี้)

## Fan-Lock Decouple — ดีไซน์ที่เลือก

**แนวคิด:** ปั๊มยังพัก 5 นาทีตามเดิมหลัง cutoff (เหตุผลด้านความปลอดภัยของปั๊มเองไม่เปลี่ยน) **แต่พัดลมไม่ต้องพักตาม** — ให้พัดลมทำงานตาม `dec.fanOn` ที่คำนวณจาก latch ปกติต่อไปได้เลยแม้ปั๊มกำลังอยู่ในช่วงพัก

**ทำไมทำได้โดยไม่ขัด invariant เดิม:** invariant `pumpOn → fanOn` (ปั๊มห้ามทำงานลำพัง) ยังคงอยู่ครบ — decouple นี้แค่ยกเลิกกฎที่บังคับ "พัดลมห้ามทำงานลำพัง" ซึ่งไม่เคยเป็น invariant จริงของระบบตั้งแต่แรก (เคส "ร้อน+ชื้นเกิน" ที่พัดลมทำงานคนเดียวไม่มีปั๊ม มีอยู่แล้วใน `auto_control_logic.h` เดิม ผ่าน test มาแล้ว) กฎ "พัดลมพักคู่ปั๊มเสมอ" เป็นแค่การตัดสินใจเสริมระดับ `.ino` (v2.3.0, 2026-07-17) ไม่ใช่ส่วนหนึ่งของ pure logic — ไม่ต้องแตะ `auto_control_logic.h` เลย

**ผลลัพธ์ duty cycle ใหม่:** พัดลมทำงานได้ต่อเนื่อง **100% ของเวลาที่ยังร้อน/แห้ง** (ไม่มี blackoutของพัดลมอีกต่อไป) มีแค่ปั๊ม/มิสท์ที่ยังพักเป็นรอบตามเดิมเพื่อความปลอดภัยของปั๊มเอง

## การเปลี่ยนโค้ดจริง (✅ ทำแล้วใน v2.6.0 — เก็บไว้เป็นบันทึกอ้างอิง)

ไฟล์เดียว: `smartfarm_firmware/smartfarm_firmware.ino`

1. บรรทัด 304: `#define PUMP_MAX_RUNTIME_MS (10UL*60*1000)` → `(15UL*60*1000)` — แก้ comment ท้ายบรรทัดจาก "10 นาที" เป็น "15 นาที" ด้วย
2. บรรทัด 305: `PUMP_COOLDOWN_MS` **ไม่แตะ** — ยืนยันแล้วว่าคงไว้ 5 นาที
3. ใน `pumpSafetyCheck()` (บริเวณบรรทัด 1148-1153): **ลบส่วนที่ตัดพัดลม + ตั้ง `fanLockUntil` ทิ้งทั้งหมด** — เหลือแค่ตัดปั๊ม (`ch4_spare=false; setRelay(PIN_RELAY_CH4,false); pumpOnSince=0; pumpLockUntil=now+PUMP_COOLDOWN_MS;`) พัดลมไม่ต้องถูกแตะเลยในฟังก์ชันนี้
4. ใน `autoControl()` ฝั่งพัดลม: **ลบเงื่อนไข `millis() >= fanLockUntil`** ออกจาก guard การเปิดพัดลม — เหลือแค่ตาม `dec.fanOn` + `!ch3_fanIn` เหมือนพฤติกรรมพื้นฐานของ latch
5. ตัวแปร `fanLockUntil` เอง: ถ้าไม่มีที่ใช้อื่นแล้วลบทิ้งได้เลย (เช็คว่าไม่มี reference เหลือที่อื่น)
6. Log/comment string ที่ยังพูดถึง "ตัดปั๊ม+พัดลม" ต้องแก้เป็น "ตัดปั๊ม" อย่างเดียว (บรรทัด 1148, 1154, 1158 และข้อความแจ้งเตือน Firebase ที่เกี่ยวข้อง) — กันข้อความหลอกตาว่าพัดลมก็ถูกตัดด้วยทั้งที่ตอนนี้ไม่ตัดแล้ว
7. Log ที่ hardcode "10 นาที" (บรรทัด 696, 1134) แก้เป็น "15 นาที" ให้ตรงกับข้อ 1
8. ไม่ต้องแตะ `auto_control_logic.h` หรือ `tests/auto_control_logic.test.cpp` เลย — logic การตัดสินใจ fan/pump ไม่เปลี่ยนสักบรรทัด
9. ทั้งหมดเป็น `#define`/logic ใน `.ino` ไม่ใช่ `volatile` threshold ที่ปรับผ่าน dashboard ได้สด — ต้อง **reflash firmware ใหม่**

## ⚠️ สิ่งที่ควรสังเกตหลัง reflash

- ช่วงปั๊มพัก 5 นาที ถ้ายังร้อน/แห้งอยู่ พัดลมจะเปิดค้างต่อเนื่อง (ไม่มีมิสท์ช่วย) — เป็นพฤติกรรมเดียวกับเคส "ร้อน+ชื้นเกิน" ที่มีอยู่แล้วในระบบ ไม่ใช่ state ใหม่ ความเสี่ยงต่ำ
- ควรเช็ค action log อีกครั้งหลัง reflash ว่าจำนวนครั้ง/สัดส่วนเวลาที่ "ไม่มีอะไรทำงานเลย" ลดลงจริงไหม เทียบกับ baseline 33% เดิม

## แนวคิดที่พิจารณาแล้วไม่ทำ (เก็บไว้กันมีคนเสนอซ้ำ)

### 1. Fan-speed staging (LOW→FULL ตามความชื้น)
ต้องการฮาร์ดแวร์เพิ่ม (พัดลมตัวที่ 2 หรือ PWM controller) — เพิ่มไม่ได้/ไม่ซื้อตอนนี้ ตัดออก 2026-07-20

### 2. Fan-start-delay (ปั๊มก่อน พัดลมหน่วงตามเวลา)
ใช้ relay เดิมได้ไม่ต้องซื้อของ แต่ตัดออกตามคำขอ 2026-07-20 เช่นกัน

### 3. สลับลำดับตาม hot+dry vs hot+humid (เสนอ 2026-07-20, เสนอซ้ำ 3 รอบ)
ข้อเสนอ: ร้อน+แห้ง → เปิดปั๊มอย่างเดียวจนความชื้น ≥75% ค่อยเปิดพัดลม / ร้อน+ชื้นอยู่แล้ว → เปิดพร้อมกันทันที
**เหตุผลที่ไม่ทำ:**
- Evaporative cooling ได้ผลดีที่สุดตอนอากาศ**แห้ง** (vapor pressure deficit สูง ระเหยเร็ว) — ร้อน+แห้งคือจังหวะที่ควรเปิดพร้อมกันทันที ไม่ใช่หน่วง สลับลำดับจะลดประสิทธิภาพช่วงที่ดีที่สุดของระบบ
- ร้อน+ชื้นอยู่แล้ว (≥75%) คืออากาศใกล้อิ่มตัว รับไอน้ำเพิ่มแทบไม่ได้ — เปิดปั๊มเพิ่มจะได้แค่น้ำท่วมเปล่าๆ ไม่ได้ความเย็นเพิ่ม (นี่คือเหตุผลที่ humid gate ปัจจุบันปิดปั๊มไว้ตรงนี้อยู่แล้ว) พัดลมก็เปิดอยู่แล้วในเคสนี้ตาม logic เดิม เปิดปั๊มเพิ่มไม่ได้ทำให้ระบายไวขึ้น
- หัวฉีดเป็นละอองหมอกจริง (0.3mm/14Bar) ไม่ใช่ sprinkle แต่สเปกจริง (`Greenhouse_Equipment_Layout_v3.md`) ระบุ spray radius 60-80cm ยังมีวิถีตกจริง ไม่ใช่แขวนลอยไม่มีที่สิ้นสุดแบบ true dry-fog — รอถึง 75% ในอากาศนิ่งไม่มีลมช่วยมีความเสี่ยงท่วมเฉพาะจุดรอบหัวฉีดอยู่
- **ที่สำคัญที่สุด:** ข้อมูล CSV จริงชี้ว่า root cause ของปัญหาคุมอุณหภูมิไม่อยู่คือ pump-safety hard-lock (ดูหัวข้อด้านบน) ไม่ใช่ลำดับเปิดปั๊ม/พัดลม — การสลับลำดับจะไม่แก้ปัญหาที่วัดได้จริงเลย

## ภาคผนวก A: ตาราง Auto Control ปัจจุบัน (ไม่เปลี่ยนแปลง)

ตารางเต็มของ logic fan/pump ที่ใช้งานจริง (จาก `auto_control_logic.h`) — ค่าปัจจุบัน: `TEMP_ON=35°C`, `TEMP_OFF=32°C`, `HUMIDITY_MIN(แห้ง)=60%`, `HUMIDITY_MAX(ชื้นเกิน)=75%` (หมายเหตุ: dashboard จริงที่เห็นแสดง 34°C/65% — เป็นค่าที่ปรับผ่าน Firebase ไว้ ต่างจาก default ในโค้ด แต่ logic รูปแบบเดียวกัน)

| Air (อุณหภูมิ + ความชื้น) | Fan | Pump | เหตุผล |
|---|---|---|---|
| ร้อน + แห้ง | ON | ON | ร้อน+แห้ง รวมกัน — จังหวะ evaporative cooling ดีที่สุด |
| ร้อน + ปกติ | ON | ON | ร้อนอย่างเดียว |
| ร้อน + ชื้นเกิน (≥75%) | ON | **OFF** | พัดลมยังระบายร้อนได้ แต่ปั๊มหยุด กันพ่นน้ำซ้ำอากาศอิ่มตัว |
| กลาง (dead-zone) + แห้ง | ON | ON | แห้งอย่างเดียว ไม่เกี่ยวกับร้อน |
| กลาง + ปกติ ⚠️ | คงสถานะเดิม | คงสถานะเดิม | โซน hysteresis |
| กลาง + ชื้นเกิน ⚠️ | ตาม latch ร้อนรอบก่อน | OFF เสมอ | humid gate ล้าง pumpHeat |
| เย็น + แห้ง ⚠️ | ON | ON | แห้งอย่างเดียว แม้อากาศเย็นแล้ว |
| เย็น + ปกติ | OFF | OFF | |
| เย็น + ชื้นเกิน ⚠️ | OFF | OFF | 2 เหตุผลพร้อมกัน |
| เซนเซอร์เชื่อไม่ได้ ⚠️ | OFF | OFF | Fail-safe ล้าง latch ทั้งหมด |

หมายเหตุ: แถว "ร้อน+ชื้นเกิน" เป็น one-way gate — ปั๊มจะไม่เปิดกลับจนกว่าอุณหภูมิจะข้าม 35°C ใหม่ (กันปั๊มกระพริบตรงเส้น 75%)
